# 관리자 API 연동 점검 (2026-10-15)

## 기준과 결과

- 계약 기준은 `api-spec/openapi.yaml`이며 Orval 입력도 이 파일이다. 과거에 `docs/openapi.yaml`이라는 낡은 사본이 있었으나 삭제했다. 기준은 이 파일 하나다.
- 계약의 **92개 HTTP 메서드 + 경로**가 모두 `backend` 컨트롤러에 존재한다. 이는 경로 대조 결과이며 모든 업무 시나리오의 실행 성공을 의미하지 않는다.
- 이번 작업에서 OpenAPI와 백엔드 계약을 변경하지 않았다. 생성 파일은 `npm run generate:api`로 갱신했다.

## 연결 범위

기존 관리자 화면의 생성 훅에 실제 인증/통신을 연결했다.

| 관리자 업무 | 기존 계약과 백엔드 구현 |
| --- | --- |
| 로그인·내 정보·로그아웃 | `/auth/login`, `/auth/refresh`, `/auth/logout`, `/members/me` |
| 회원·강사 계정 | `/members`, `/members/{memberId}`, 상태·권한 API |
| 강사 가능시간·퇴사·즉시 수업 인계 | `/instructors`, `/members/{memberId}/availability`, `/resignation`, `/lesson-reassignments` |
| 부재 조회·승인·반려·취소 | `/absences` 및 개별 처리 API |
| 수업·시간표·공개 상태·취소 | `/lessons` 및 개별 처리 API |
| 예약·출결 | `/reservations`, `/lessons/{lessonId}/reservations`, 취소·출결 API |
| 이용권·홀딩 | `/passes`, 개별 수정·홀딩·홀딩 해제 API |
| 결제 기록·환불 표시 | `/payments`, `/passes/{passId}/payments` 및 개별 처리 API |
| 상품·룸·수업 유형 | `/pass-products`, `/rooms`, `/lesson-types` |
| 영업시간·예약 정책 | `/business-hours`, `/reservation-policy` |
| 수당·정산 | `/members/{memberId}/pay-rates`, `/settlements` 및 검토·확정·지급 API |
| 알림·활동 이력 | `/notifications`, `/activity-logs`, `/activity-log-actions` |
| 기본 운영·매출 통계 | 기존 목록의 전체 건수 또는 전체 페이지를 사용해 계산 |

Access Token은 메모리에만 보관하고 요청에 Bearer 헤더를 넣는다. Refresh Token은 서버의 HttpOnly 쿠키로 전달한다. 새로고침 시 세션을 복원하고, 인증된 업무 요청의 401에는 한 번 갱신 후 재시도한다. 동시 갱신을 하나로 합치고 갱신 실패 시 캐시를 비우고 로그인 화면으로 돌아간다. 로그인 실패·403·일반 서버 오류는 토큰 갱신으로 처리하지 않는다.

관리자 날짜 입력·수업 수정/출결 가능 시각·홈 집계는 현재 서울 날짜/시각을 쓴다. 모의 모드에서는 기존 예시 기준일을 유지한다. 전체 집계 및 선택 목록은 생성된 infinite 훅으로 모든 페이지를 조회한다. 일반 업무 목록은 기존 5개 단위 서버 페이지를 유지한다.

## 현재 없는 API 또는 계약 필드

다음 항목은 프론트에서 임의로 저장 완료 처리하지 않는다. 추가 구현을 원하면 `AGENTS.md`에 따라 변경안을 승인받은 뒤 기준 OpenAPI부터 수정해야 한다.

| 화면 기능 | 부족한 계약 | 현재 동작 / 검토할 변경 |
| --- | --- | --- |
| 강사별 시간표 색상 공유 | 강사 색상 조회·저장 필드/API | 브라우저에만 저장. 선택 필드와 저장 API 추가는 기존 사용을 유지하도록 설계 가능 |
| 퇴사 전 인계 대상 예약·진행 상태 | 예정 인계 대상 저장·조회와 진행 상태 | 현재 인계 API는 미래 수업의 담당자를 **즉시** 변경. 예약 인계 모델 추가 필요 |
| 반복 수업 생성·범위 수정 | 반복 규칙, 회차 관계, 선택/이후 회차 일괄 처리 | 개별 수업 개설·수정만 가능. 기존 개별 API와 별도 추가 가능 |
| 예약 승인·거절·대기자·자동 승급 | 신청/대기 상태와 순서, 승인·승급 처리 | 현재 즉시 확정 방식. 상태 enum 및 예약·차감 규칙 변경은 기존 클라이언트 호환성 검토 필요 |
| 이용권 상품 판매 중지·재개 | 판매 상태와 변경 API | 상품 수정 및 발급 이력 없는 상품 삭제만 가능 |
| 룸 비활성 | 활성 여부와 배정 제한 정책/API | 룸 수정 및 사용 예정 수업 없는 룸 삭제만 가능 |
| 날짜별 특별 휴무·일괄 보상 | 날짜별 휴무와 대상 이용권 보상 처리 | 요일별 영업시간/정기 휴무만 가능. 중복 보상·취소 기준 확정 필요 |
| 출결 정정 사유·별도 승인 | `AttendanceRequest`에 사유 없음, 정정 요청/승인 API 없음 | 관리자는 기존 출결 값을 직접 변경. 활동 이력은 조회 가능하지만 입력 사유를 서버에 남길 수 없음 |
| 신청일/취소일 기준 발생 통계·재등록 통계 | 해당 기준의 조회 필터/전용 집계 없음 | 현재 통계는 수업일 기준 현재 예약 상태, 발급일 기준 이용권, 결제일 기준 매출. 대규모 데이터에는 서버 집계 API 추가 권장 |

색상·판매 상태·룸 상태 등의 필드/API를 추가하는 것 자체는 기존 계약을 유지하는 방식으로 설계할 수 있으나, 실제 배정·발급 제한이나 필수 필드 도입은 별도 호환성 검토가 필요하다. 위 내용은 변경 후보이며 승인 또는 스펙 변경 완료를 의미하지 않는다.

## 백엔드 운영 준비 사항

- 이메일 인증, 관리자 초대, 비밀번호 재설정은 API가 있으나 `LoggingEmailVerificationMailer`, `LoggingPasswordResetMailer`가 개발용 코드/토큰을 로그로 출력한다. 실제 이메일 발송 구현이 필요하다.
- 새 DB에는 기본 관리자 계정이 없다. 실제 사용에는 팀원이 준비한 관리자 계정/초기화 절차가 필요하다. 미리보기의 `admin@rha.example`은 실제 계정이 아니다.
- 로컬은 Vite의 `/v1` 프록시를 통해 접근한다. 배포에서도 같은 출처의 `/v1` 역방향 프록시와 HTTPS를 사용하면 현재 Secure·SameSite=Strict 쿠키 정책을 유지할 수 있다. 별도 도메인 직접 호출은 백엔드 CORS·쿠키 정책 검토가 필요하다.
- 이번 업무 연결 범위는 관리자 화면이다. 기존 강사 담당 수업/부재 UI의 메모리 상태와 회원·강사 홈 예시 전체를 실제 API로 전환한 작업은 아니다.

## 실행과 검증

```bash
# DB
cd backend
docker compose up -d
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew bootRun

# 별도 터미널
cd frontend
npm ci
npm run dev:api
```

`npm run dev`는 DB 없이 이용하는 모의 모드다. 회원가입 없이 로그인 화면의 **회원 화면 열기 / 강사 화면 열기 / 관리자 화면 열기** 버튼으로 바로 들어갈 수 있다. 관리자 예시 계정(`admin@rha.example` / `RhaDemo123!`)을 직접 입력해도 된다. 실제 연동은 백엔드·DB·관리자 계정을 준비한 뒤 `npm run dev:api`로 실행한다. 다른 서버를 사용할 때는 `frontend/.env.local`에 `API_PROXY_TARGET=http://localhost:8080`을 지정한다. 모드 변경 시 개발 서버를 재시작한다. 프로덕션 빌드는 항상 실제 API를 사용한다.

검증 내용:

- 프론트 타입체크·프로덕션 빌드, 통신/세션 회귀 테스트(동시 401, 권한 오류, 갱신 실패, 계정 전환, 204 응답 등).
- 별도 임시 DB에서 브라우저로 관리자 로그인 → 룸 저장 → 새로고침 후 세션 복원 및 저장 데이터 유지 → 로그아웃을 확인.
- 101명의 테스트 회원으로 100건 이후 페이지까지 운영 통계에 합산되는 것을 확인.
- 최초 연동 검증 기준(`c0d76e5`)에서 백엔드 전체 **1,304개 테스트 통과**(실패/오류/건너뜀 0). PR 준비 시 최신 `main`의 동시성 수정은 반영했으며, 이 수치는 그 수정 전 검증 결과다. 테스트 명령은 `./gradlew test`. Docker Desktop 소켓/구버전 docker-java 호환 문제 발생 시 현재 로컬 검증에는 다음 실행 환경을 사용했다(프로젝트 설정 변경 없음).

```bash
DOCKER_HOST=unix://$HOME/.docker/run/docker.sock \
JAVA_TOOL_OPTIONS=-Dapi.version=1.44 \
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew test
```
